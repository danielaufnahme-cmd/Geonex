# Geonex — Initial Language Vision and Design

## 1. What Geonex is about

Geonex is going to be a programming language that sits somewhere between Python and Java/C++.

Python is very readable and can feel almost like English. Java and C++ are generally more detailed and can be harder to write. Geonex should be somewhere in the middle.

The goal is for Geonex to be:

- easier to write than Java and C++
- more structured and explicit than Python
- faster than Python
- focused on good performance
- readable and simple

The main target is developers who want to build applications with a language that is easy to code and understand, while still having good performance.

My main priorities are:

1. **Readability**
2. **Performance**
3. **Simplicity**

I want Geonex to be especially easy to read and write compared with most languages, while still being significantly faster than Python.

In a simple way, I think of Geonex as what would happen if Python and Java/C++ had a child.

---

## 2. How the language should look

Geonex should have a syntax that combines ideas from Python and Java/C++.

For example, printing should use:

```geonex
println("Hello");
```

for printing a line, and:

```geonex
print("Hello");
```

for printing without automatically creating a new line.

Geonex will use semicolons, similar to Java and C++.

Variables will explicitly specify their type.

For example:

```geonex
int age = 15;
```

The general structure is:

```text
type → variable name → value
```

The language should have the normal basic programming features, including:

- variables
- data types
- loops
- functions
- operators
- strings
- conditions

This is the starting point of the language, and the exact design of many features can be decided later.

---

## 3. Compilation and execution

Geonex will initially have a compiler so that Geonex source code can be compiled and then executed like a normal programming language.

Later, I want to create the **GVM (Geonex Virtual Machine)**.

The GVM would be similar to the Java Virtual Machine, but designed specifically for Geonex.

The general idea would be:

```text
Geonex source
      ↓
   Compiler
      ↓
Geonex bytecode
      ↓
      GVM
      ↓
   Operating system
```

The reason for using a virtual machine is portability.

If the GVM can run on a device, Geonex programs should be able to run on that device without needing a completely different version of the language for every platform.

---

## 4. Memory management

Geonex should have automatic memory management.

I do not want programmers to have to manually manage memory like they often do in C++.

Geonex should have an automatic garbage collector.

The exact way memory management and garbage collection will work has not been decided yet. This is something that can be designed later as the language and runtime develop.

---

## 5. Libraries

Geonex will have standard libraries and an import system.

Libraries should be imported using a simple syntax such as:

```geonex
import libraryName;
```

One of the long-term goals is interoperability with existing libraries.

In particular, I would like Geonex to eventually be able to use Python libraries.

The idea is that developers could import and use Python libraries from Geonex without having to rewrite those libraries.

This is a long-term goal, however, and the exact technical implementation has not been decided yet.

---

## 6. Long-term vision

The language is still at a very early stage.

Many things have not been decided yet, and this document represents my current thinking rather than a final specification.

The main idea is to create a language that combines:

**Python's readability and simplicity**

with

**Java/C++-style structure and performance.**

Geonex should eventually have its own compiler, bytecode format, virtual machine, standard library, and broader ecosystem.

For now, the most important thing is to establish the basic language design and gradually build the technology needed to make it real.
